# CampusConnect — Infrastructure Overview (as of 2026-08-05)

Bird's-eye view of everything real and currently live in Azure + Kubernetes for the CampusConnect capstone.
Everything below has been applied for real and verified — not aspirational.

## 1. Where things stand, in one paragraph

The app (FastAPI + Next.js + RQ worker) runs as 4 real services inside a real AKS cluster, in a hub-spoke
VNet, talking to a real private Postgres database, with all secrets sourced from Key Vault. An NGINX Ingress
gives it a single public entry point, and an HPA autoscales the API under load (proven with a real load test).
There is **no CI/CD pipeline yet** and **no GitHub repo yet** — the app has only ever been deployed by typing
commands live in class. That's today's (Aug 5) first job.

## 2. Azure resources — `rg-campusconnect` (region: `centralindia`)

| Spoke VNet | `campusconnect-spoke-vnet` | `10.1.0.0/16`. Peered bidirectionally with the hub. |
| Subnet: AKS | `snet-aks` | `10.1.1.0/24`. AKS nodes live here. |

| NSG (AKS) | `nsg-snet-aks` | `AllowVnetInBound` + `AllowLoadBalancerProbeInBound` + `AllowInternetToNodePortInBound` (both on `30000-32767`, source `AzureLoadBalancer`/`Internet` — see §6, needed for the Ingress LB to actually reach nodes). |
| NSG (DB) | `nsg-snet-pe` | `AllowVnetInBound` only. |
| AKS Cluster | `aks-campusconnect` | Single node pool, `Standard_D2s_v5`, `SystemAssigned` identity, `oidc_issuer_enabled=true`. |
| ACR | `acrcampusconnectceb383` | Basic SKU. AKS's kubelet identity has `AcrPull` role on it — no registry password anywhere. |
| Postgres | `psql-campusconnect` | Flexible Server, Postgres 16, `B_Standard_B1ms`, 32GB. `public_network_access_enabled=false`. Reachable **only** from inside the spoke VNet. |
| Private DNS Zone | `privatelink.postgres.database.azure.com` | Linked only to the spoke VNet — the Postgres hostname resolves to a private IP inside the VNet and fails to resolve from anywhere else. |

All of the above is defined as Terraform in `infra/*.tf` and was provisioned with `terraform apply` — it is
fully reproducible from empty. **Not yet in Terraform:** the Ingress Controller and the Ingress/HPA resources
(§4) — those were installed imperatively (Helm + `kubectl apply`) and are not currently reproducible by
`terraform apply` alone. Worth moving into Terraform if time allows; not blocking anything today.

## 3. The database — how it's actually secured

- **Mechanism:** VNet integration (subnet delegation), not a Private Endpoint. Different Azure feature, same
  outcome as Day 12's Storage lesson: no public path in.
- **Password:** machine-generated by Terraform (`random_password`, 24 chars, **no special characters**). This
  was a deliberate fix after a real bug chain: a hand-typed password containing `@` broke the connection-string
  URL parser, and percent-encoding it to fix that then broke Alembic's `configparser` (which treats `%` as
  interpolation syntax). Root fix: never put special characters in the password to begin with.
- **Proof it's actually private:** a pod running *inside* AKS resolves the hostname and connects fine
  (`psql` from a `kubectl run` test pod lists all 11 tables). A DNS lookup for the same hostname from *outside*
  the VNet fails outright — no route to the private zone.
- **Schema:** applied via a real `kubectl run migrate` job (`alembic upgrade head && python seed.py`). 11 tables
  exist; 4 forums are seeded (Placement Prep, Computer Science, Electronics & Comm., Hackathons).

## 4. Kubernetes — what's actually running (namespace: `default`)

| Deployment | Replicas | Image | Notes |
|---|---|---|---|
| `redis` | 1 | `redis:7-alpine` | In-cluster only — queue broker for RQ, deliberately NOT a managed Azure service (Day 16 decision: system-of-record goes managed, transient queue state doesn't need to). |
| `api` | 2–6 (HPA) | `acrcampusconnectceb383.azurecr.io/campusconnect/api:v1` | FastAPI. Reads `DATABASE_URL`/`REDIS_URL`/`JWT_SECRET`/`CORS_ORIGINS` from the `campusconnect-secrets` K8s Secret. Probes on `/health` (which itself checks DB connectivity). |
| `worker` | 1 | `.../campusconnect/worker:v1` | RQ consumer. No probes — no HTTP port to check; relies on RQ's reconnect logic + K8s crash-restart. |
| `frontend` | 2 | `.../campusconnect/frontend:v1` | Next.js, built with `NEXT_PUBLIC_API_URL=/api` baked in at image-build time — same-origin, no CORS, works only because of the Ingress rewrite below. |

**Secret** `campusconnect-secrets` — created manually via `kubectl create secret generic --from-literal=...`,
values pulled from Key Vault at deploy time with `az keyvault secret show`. Nothing is synced automatically;
if the Key Vault value changes, the K8s Secret must be recreated and `api`/`worker` restarted. (The Secrets
Store CSI Driver — auto-sync, no manual step — remains a documented stretch goal, not yet built.)

**Ingress** (`ingress-nginx`, installed via Helm, `LoadBalancer` type, external IP currently `4.247.216.29`):
- `/` → `frontend:3000`
- `/api(/|$)(.*)` → `api:8000`, with `rewrite-target: /$2` (the api's own routes have no `/api` prefix, so this
  strips it before forwarding)
- This is what makes the frontend's relative `/api` calls actually resolve — same origin, no CORS needed, and
  the httpOnly auth cookie flows naturally.
- **Real gotcha already fixed:** the AKS subnet uses a hand-authored NSG (not AKS's own auto-managed one), so
  the Load Balancer's health probes and forwarded client traffic were silently blocked until two NSG rules were
  added explicitly (see §2, `nsg-snet-aks`). Without that fix, `curl` to the Ingress IP just times out with no
  error.

**HPA** on `api`: min 2, max 6 replicas, target 50% average CPU utilization (relative to each pod's 100m
request). Proven live: a real `hey`-based load test spiked CPU to 257%/50%, HPA scaled 2→6 (one pod stayed
`Pending` — single-node cluster hit its own CPU capacity, an honest and expected constraint, not a bug), then
scaled back down to 2 within the standard ~5 minute cooldown window after the load stopped.

## 5. Verified end-to-end (against the real cloud deployment, not mocks)

Register → login → logout (401 enforced after) → create post → comment → like → create forum thread → reply →
create project → request to join → accept the request → notification generated by the **async worker** for
every one of: comment, like, team_request, team_request_update. All tested via real HTTP calls through the
Ingress's `/api` path, exactly as the browser will use it.

## 6. Real bugs hit and fixed along the way (worth remembering, not repeating)

1. **`npm ci` lockfile mismatch** in the frontend Docker build → switched to `npm install`.
2. **Empty `frontend/public/` not surviving the zip** → added a real file (`robots.txt`).
3. **`LocationIsOfferRestricted`** — Postgres Flexible Server isn't offered in `eastus` for this subscription.
   Checked real availability with `az postgres flexible-server list-skus --location <region>`; `centralindia`
   came back clean. The entire resource group was rebuilt there (Postgres must share a region with its VNet).
4. **`Standard_D2s_v7` unavailable in centralindia** → switched to `Standard_D2s_v5`.
5. **Password `@`-character bug chain** → see §3. Root-fixed with `random_password(special=false)`.
6. **AKS custom-NSG blocking the Ingress LoadBalancer** → see §4. Root-fixed with two explicit NSG rules.

## 7. What's explicitly NOT done yet

- No GitHub repository exists for this project yet.
- No CI/CD pipeline (GitHub Actions) exists — every deploy so far has been a manual, live-typed command.
- No Trivy scan gate, no branch protection.
- Ingress + HPA are not yet expressed as Terraform (installed imperatively).
- No staging/prod environment separation — everything above is one single environment.
- No Prometheus/Grafana on this cluster yet (Day 14 had this on a different, now-deleted cluster).
- No security-hardening pass has been done specifically on this deployment.
- Final teardown of all of the above has been deliberately deferred until the remaining sessions are complete.
